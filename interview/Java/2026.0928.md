### 1.谷粒商城库存怎么不超扣？

    S—情景 

总库存stock,已锁定库存stock_locked，可用库存两者相减。超扣是秒杀/大促场景下，同一个sku可能有成百上千的请求打过来，多个线程都认为"可用库存 = 1",都认为够，都去扣，就会出现stock_locked > stock。
    T —任务

在分布式、高并发的场景下，既需要保证“不超买”，也需要保证“不误伤（因重复提交、死锁、超时未付款、服务调用失败，把库存永久锁死，导致"有货卖不出去"）
    A — 行动

▎ 我做了六层，但我先说最关键的一层。

第一层，核心：数据库 CAS

▎ 真正的正确性就靠这一条 SQL：
▎
▎ UPDATE wms_ware_sku SET stock_locked = stock_locked + ?
▎ WHERE ware_id = ? AND sku_id = ? AND (stock - stock_locked) >= ?
▎
▎ 关键在于把判断和修改压进同一条 UPDATE。InnoDB 执行时先对命中行加排他锁，(stock - stock_locked) >= ? 这个条件是在拿到行锁之后用最新值求值的。所以并发请求被强制排队：第二个请求拿到锁的时候，看到的已经是第一个请求扣完的值，条件不成立，影响行数是 0。
▎
▎ 判断和扣减之间没有任何窗口期，这就是防超卖的根本。不是"先查再改"，而是让数据库帮我做 compare-and-set。

第二层：全有或全无

▎ 一个订单可能跨多个仓库、多个商品，所以是批量锁。batchUpdate 会返回每条 UPDATE 的影响行数，我逐条校验，任意一条是 0 就抛库存不足异常，方法上的 @Transactional 把整批已经成功的扣减全部回滚。
▎
▎ 不会出现"A 商品锁上了、B 商品没锁上"这种半截订单。

第三层：防死锁

▎ 批量锁多行的时候，如果两个事务加锁顺序相反就会死锁。所以锁之前先把明细按仓库 ID 和商品 ID 升序排序，保证所有事务的加锁顺序全局一致。解锁路径用的是同一套排序，两侧对齐。

第四层：入口防重

▎ 提交订单接口加了防重复提交注解，底层是 Redis 的 SETNX。用户手抖点两下、或者网络重试，第二发直接被打回。这一层挡的是重复下单，不是防超卖，但能大幅削掉无效流量。

第五层：超时自动释放

▎ 锁了库存用户不付款，库存就白占了。所以锁成功后会写一张库存工作单，记录每个商品在哪个仓锁了多少、当前是"已锁定/已解锁/已扣减"，然后发一条 TTL 加死信的延迟消息。
▎
▎ 消息过期后进消费队列，消费者先查订单状态，只有订单不存在或者已取消才真正解锁，然后手动 ACK，失败就 NACK 重回队列。
▎
▎ 订单侧同理，30 分钟没付款自动取消。这里有两个细节我认为比较关键：
▎ 一是取消订单用 UPDATE ... WHERE status = 待付款，靠数据库行锁做 CAS，避免"先查后改"的并发漏判；
▎ 二是消息不是直接发的，而是先写本地消息表，在事务的 afterCommit 回调里才真正投递，防止"事务回滚了但消息已经发出去了"。

第六层：解锁也做 CAS

▎ 解锁的 SQL 是 SET stock_locked = stock_locked - ? WHERE ... AND stock_locked >= ?。这个 stock_locked >= ? 有两个作用：一是保证不会把锁定库存减成负数；二是让重复投递的消息变成幂等操作——第二次执行影响行数是 0，直接拒收，不会把库存重复还回去。

R — 结果

▎ 结果是超卖在数据库层面被彻底堵死了，不依赖应用层加锁，也不依赖先查后改，代码路径短、推理简单，review 的时候一眼能看出来是对的。
▎
▎ 库存占用也有了完整的生命周期闭环：锁定 → 付款扣减 / 超时取消 → 解锁，未付款的库存最长 30 分钟自动还回池子。
▎
▎ 不过我也想补充两个我当时权衡过、现在回头看值得改进的点：
▎
▎ 一是跨服务没有分布式事务兜底。锁库存是 Dubbo 调到库存服务的事务，订单落库是订单服务自己的事务，项目里订单链路没用 Seata。极端情况下"锁库存成功、订单落库失败"，库存会挂住。目前靠延迟消息的兜底释放，但那条消息本身没走本地消息表，理论上仍可能丢——这是我会优先补的一环。
▎
▎ 二是热点商品全部压在数据库行锁上，秒杀场景下会有明显的锁竞争。更彻底的方案是 Redis 用 Lua 做预扣减，数据库只做异步落单。但在我这个业务量级下，我认为先保证正确性、把复杂度留在数据库里，是更划算的选择。

### 2.你使用过缓存吗？

像是商品多级分类树，在主页，商品列表页，后台的商品发布页都需要使用，读极多写少，适合使用缓存。SpringCache 是 Spring 提供的一套缓存抽象层（AOP 实现），用注解给方法加缓存,**底层可以切换成内存、Redis、Caffeine 等多种缓存实现** 。

#### 2.1 缓存穿透

简单来说就是查数据库中不存在的数据。解决方法有 缓存空对象？布隆过滤器两种方案。

SpringCache默认允许空对象存在，CacheManager 默认 allowNullValues = true，SpringCache 会把查不到的结果写成一个 NullValue 哨兵对象存进 Redis。下次同样的请求进来直接命中这个哨兵，不会再落到数据库。

布隆过滤器相当于bit数组+k个hash函数。bit数组初始全为0,然后缓存一个新数据就会经过k个hash函数计算出k个下标，下标对应的bit位置为1。那么最终只要任意一个 bit 位是 0 ,该数据一定不存在，会被过滤掉。但是即使所有 k 个 bit 位全是 1 → 元素可能存在（假阳性 / 误判）。
key 数量巨大、大量非法请求，允许少量误判 → 布隆过滤器（商品详情)；key 不多、非法查询很少，直接缓存空对象更简单（商品分类树)

#### 2.2 缓存雪崩

就是大量的热点数据同时过期，解决方法就是把过期时间打成随机值。

如果是redis宕机导致的整个实例的缓存雪崩，那就得靠降级机制，比如CacheManager 在 Redis 之上套了一层 Caffeine 本地缓存，写入后 30 秒过期、最多 1000 条。

#### 2.3 缓存击穿

单个热点数据过期，大量并发请求打到数据库。解决方法`设置锁，只让第一个请求去查询 mysql 并缓存，其他等待缓存中数据`。

我的做法是在 @Cacheable 上加 sync = true。它的语义是：同一个 key 并发加载时，只有一个线程真正去执行方法查库，其他线程阻塞等待结果，拿到之后共享。但是synchronized 锁的互斥范围只有单个jvm实例，集群失效。

其他方法：

一个是原生 Redis 实现：SETNX 抢锁、抢不到自旋等待、拿到锁后 double-check 再查库（因为等锁期间前一个线程可能已经写好了缓存）、然后写缓存、最后用 Lua 脚本比对 UUID 再删除来释放锁——用 Lua 是为了保证"判断是不是自己的锁"和"删除"这两步的原子性，防止误删别人的锁；释放放在 finally 里，防止查库抛异常导致锁泄漏。
另一个是 Redisson 版本：直接 getLock + lock/unlock，配合 RMapCache 支持带 TTL 的写入。Redisson 的锁自带看门狗续期，不用自己处理锁超时的问题。

#### 2.4 一致性

 写操作我全部挂了 @CacheEvict，更新完直接让缓存失效，下次读自然回源重建——不做更新缓存，因为"更新缓存"在并发下容易产生旧值覆盖新值的乱序问题，而"删除缓存"是幂等的、天然安全的。
另外这层 CacheManager 默认开了事务感知：evict 会被包在一个 TransactionAwareCacheDecorator 里，只有数据库事务提交成功后才真正删除缓存。这就避免了"事务回滚了但缓存已经被删掉"或者更糟的"缓存删了、事务回滚、数据没变"这种无意义的缓存穿透。

效果上，分类树这类高频读接口基本不再打数据库，Redis 的 QPS 压力也被 Caffeine 一级缓存削掉一大截。
